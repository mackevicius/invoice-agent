# API organised by layer

The Python API is organised by layer (`routes/`, `schemas/`, `services/`, `clients/`, `workers/`, `db/`), not by feature like the web app. One folder per kind of code makes the architecture readable at a glance for a team new to Python. The cost is that a feature ticket usually touches several folders, so a feature keeps the same file name in each layer (`routes/invoices.py`, `schemas/invoices.py`, `services/invoices.py`). Imports only point down the layers: `routes` → `workers` → `services` → `clients`/`db` → `schemas`; a layer may skip the ones below it. HTTP details (cookies, status codes, `fastapi` imports) stay in `routes`; SQL stays in `services` and `db`. `app.py` is the only module that wires the parts together, and nothing outside `routes` imports `routes` except `app.py`. We would revisit this if the API grows past roughly 50 modules and features start to blur together inside each layer.
